# AI-Agent Maintainability

A reference doc on what it currently takes for an AI coding agent (not a human) to make a change to this codebase and actually know whether it worked, without a human in the loop checking screenshots or running the app by hand. Written against the post-ADR-010 architecture (video export primary, live players debug-only).

## Why this matters

This repo is unusually agent-friendly already (deterministic seeded cursor noise, manifest-driven rendering, no live network calls during replay) but most of that determinism was built for human review, not agent self-verification. As more of the actual editing work on this codebase is done by agents rather than humans, the binding constraint shifts from "can a human eyeball the diff" to "can an agent, working alone in a sandbox with no browser and no display, confirm a change is correct before reporting it done." That gap is real today — this session hit it directly (see "What's missing" below) and worked around it ad hoc each time rather than relying on a built-in mechanism.

The other reason this matters: idempotency and verification are the same property looked at from two angles. A pipeline an agent can safely re-run to check its own work (hash-based narration skip, capture that merges instead of overwrites) is also a pipeline a human can safely re-run without fear of silent regressions. Investing in agent-verifiability and investing in pipeline robustness are not two separate asks — most of the concrete next steps below serve both.

## What verification options exist today

Roughly in order of how much they actually prove:

- **Static checks — cheap, narrow, reliable.** `node --check <file>.mjs` catches syntax errors. `python3 -m json.tool <file>.json` catches malformed JSON. TypeScript files can be checked with `tsc --noEmit` (not yet wired into a single command anywhere in this repo — currently ad hoc, run by hand against whichever file changed). These prove a file parses; they prove nothing about behavior.
- **ffprobe on exported videos — cheap, decent signal.** Confirms codec (`hevc`/`hvc1`), container, resolution, frame rate, duration, audio stream presence/codec. Catches "the pipeline produced a corrupt or empty file" reliably. Does not catch "the video looks wrong" (wrong frame order, misplaced cursor, garbled compositing).
- **Frame extraction + visual inspection via the Read tool — the strongest check available in this sandbox, but manual and slow.** `ffmpeg -vf select=...` to pull a specific frame as a PNG, then Read it as an image. This is how the asyncWait full-frame export was actually confirmed coherent in this session (checked the first and last frames of the compressed wait, saw the progress bar and spinner in the right state, no layout-shift artifact). It works, but it's a human-style visual spot-check performed by an agent rather than something with a pass/fail signal — there's no automated "this frame matches expected" assertion, just an agent looking at a picture and describing what it sees. Scales badly: nobody is going to spot-check every frame of every export, every time.
- **Byte-for-byte / hash diffing against a known-good reference — cheap and strong, but only exists ad hoc today.** Used once already in this codebase's history (the scroll-frame dedup bug was caught via `md5sum` across captured frames — see roadmap.md's scroll-showcase entry) but there's no standing "golden output" fixture + comparison script; it was a one-off debugging technique, not a repeatable check.
- **Manual re-reading of edited files for brace/logic correctness — the weakest, used only when nothing else was available.** The original asyncWait prototype (per roadmap.md) was verified this way because no browser was available at all in that sandbox to run it. This is the agent-verification equivalent of "looks right to me" — better than nothing, but it's the fallback of last resort, not a method that should be relied on if any of the above are available.

## What's missing or weak

- **No real browser in this sandbox, at all.** Playwright capture (`capture/playwright`) cannot be run here — confirmed repeatedly this session and in prior sessions (network allowlist blocks the Chromium download). Any change to capture-side code (`capture-demo.ts`, `capture-session.ts`) can be statically checked and read carefully, but never actually executed end-to-end in this environment. This is a hard environmental limit, not a code-quality gap, but it means a whole category of bugs (real Playwright API behavior, real page timing) is invisible to an agent working here no matter how good its other checks are.
- **No automated frame-correctness assertions.** Every visual verification this session did (asyncWait frame inspection, scenario-1 regression) was "agent looks at an image and narrates what it sees," not a script that returns pass/fail. There's no equivalent of a snapshot-testing library (e.g. comparing a rendered frame against a stored reference PNG with a pixel-diff threshold) anywhere in the pipeline.
- **No test suite.** There is no `npm test` anywhere in this repo (across `shared/`, `capture/playwright/`, `replay-app/`, `scripts/`) as of this writing. `buildTimeline()`/`sampleAt()` — the most duplication-prone, most-forked logic in the codebase (now three independent copies: `player.js`, `replay-player.component.ts`, `build-frame-plan.mjs`, per ADR-009's own flagged risk) — has zero unit tests verifying the three copies agree on the same input. An agent changing one copy has no automated way to know if it silently drifted from the other two; it has to manually diff logic by eye, which is exactly the failure mode ADR-009 already flagged as a known risk.
- **Environment file-sync unreliability discovered this session.** The Write/Edit tools' own "success" response was not a trustworthy signal that the change actually landed on the bash-visible disk in this sandbox — twice this session, a tool reported success while the underlying file was left truncated or padded with stray NUL bytes, only caught by independently checking with `wc -c`/`node --check`/`python3 -m json.tool` from the bash side. An agent that trusts its own editing tools' status messages without an independent disk-level check can silently ship a broken file while believing the edit succeeded. This is the single most concrete maintainability risk found this session — worth treating as a standing practice (verify via bash after any edit to a file that's about to be executed/parsed) rather than a one-off curiosity.
- **No idempotency guarantee on capture.** The narration-wiping bug under investigation (capture appears to overwrite `manifest.json` wholesale rather than merging) is exactly an idempotency failure — re-running a step an agent (or a human) believes is "safe to re-run to double check" actually destroys existing state. An agent cannot safely re-verify its own work by re-running capture if doing so has a side effect of silently deleting unrelated narration data.
- **No content-addressed regeneration anywhere yet.** Narration audio regenerates unconditionally rather than comparing against a stored hash of the source text (the hash-based narration work tracked separately in this session's task list addresses this directly for narration; the same gap likely exists wherever else this codebase regenerates derived artifacts from source data).
- **Fragmented entry points.** Scripts live across `scripts/`, `capture/playwright/`, and `replay-app/`, each with its own `package.json`/invocation convention. An agent (or a human) has to already know which subfolder owns which step to run anything — there's no single documented command sequence for "capture → narrate → export" from the repo root. This doesn't break verification directly, but it raises the cost of every verification attempt, which in practice means fewer of them happen.

## Next steps (concrete, roughly ordered by leverage)

1. **Treat bash-side disk verification as a standing step, not an exception.** After any edit to a file that will be executed or parsed (`.mjs`, `.json`, `.ts`), independently confirm via the shell (`node --check`, `python3 -m json.tool`, `wc -c` against expected size) rather than trusting the editing tool's own success message. Cheapest fix on this list; already informally adopted mid-session, worth writing down so it isn't lost.
2. **Add a minimal unit-test harness for `buildTimeline()`/`sampleAt()`.** Even a handful of fixed-input/expected-output cases run against all three copies (`player.js`, `replay-player.component.ts`, `build-frame-plan.mjs`) would catch the exact drift risk ADR-009 already flagged, and would give an agent a real pass/fail signal instead of a manual diff-by-eye when touching any of the three.
3. **Build one small golden-frame fixture with a pixel-diff check.** Render a known scenario's frame N, store the reference PNG, add a script that re-renders and compares (allow a small tolerance for font/AA differences) — turns "agent looks at a frame and narrates it" into an actual pass/fail check, at least for the cases the fixture covers.
4. **Fix capture idempotency (manifest merge, not overwrite).** Already in progress as a tracked bug fix this session — listed here because it's also a maintainability prerequisite: an agent can't use "re-run capture" as a safe verification step until re-running it stops being destructive.
5. **Extend hash-based regeneration beyond narration once proven there.** If the narration text-hash approach works well, the same pattern (store a hash of the input, skip regeneration if unchanged) is likely applicable to any other derived-from-source-data step in this pipeline — frame-plan generation from manifests is a plausible second candidate.
6. **Consolidate entry points (root-level CLI).** Already in progress as a tracked task this session — included here because lowering the cost of running any one step raises how often an agent will actually run it as a verification step rather than skip it under time/effort pressure.
7. **When real-browser verification genuinely matters, say so explicitly rather than silently downgrading to manual review.** Capture-side changes in this sandbox cannot be run end-to-end; the honest thing for an agent to report is "verified by static check + careful reading, NOT executed — needs a real run on a machine with a browser," not to quietly treat the manual reading pass as equivalent confidence. (This doc itself follows that practice — see the caveats throughout ADR-010's verification section about what was and wasn't actually run.)

## Workplace-reuse note

This doc is intentionally written generically enough to be a starting checklist for any other codebase where an agent works largely unsupervised: what static checks exist, what "real" execution checks exist, what's missing, and a concrete near-term punch list. The pattern that generalizes best from this session is #1 above (don't trust an editing tool's own success signal — independently verify from the execution environment) since it's the one failure mode least specific to this particular pipeline.
