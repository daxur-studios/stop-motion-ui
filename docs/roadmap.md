## Feature: Headless video export — ✅ Done (now two pipelines — see ADR-012)

- Exports a scenario (screenshots + bezier cursor motion + circle gestures + asyncWait full-frame cycling + TTS narration) as a real compressed `.mp4`, instead of only playing live in-browser. **Video export is now the primary deliverable; the live in-browser players are an internal debug/preview tool only — see ADR-010.**
- **As of ADR-012, there are two export pipelines, kept side by side on purpose:**
  - **Canonical (what the Angular "Export Video" button and `npm run export-video` now both run):** `node scripts/cli.mjs export <scenario-dir> [...]` → `scripts/playwright-export.mjs`. Launches real headless Chromium, drives the **live** `replay-app` canvas via `window.__stopMotion.seekTo()/waitForReady()`, screenshots `#stage` frame-by-frame (pixel-identical to the live player, badge/ripples/cursor included for free), then ffmpeg-mixes audio and encodes with the same settings as below. Requires `npm run dev` already running (Angular dev server on :4221) and a real launchable browser — **not runnable in a sandboxed/CI/agent environment with no browser** (see `docs/agent-maintainability.md`).
  - **Legacy (sandbox/CI-safe fallback):** `node scripts/cli.mjs export <scenario-dir> --legacy` → `scripts/export-video.mjs`. `scripts/build-frame-plan.mjs` (Node port of `buildTimeline()`/`sampleAt()`/`drawRipples()` math, no rendering) → `scripts/render-frames.py` (Pillow rasterizes to a PNG sequence) → `ffmpeg`. No browser or live dev server required — only Node, Python3+Pillow, ffmpeg.
  - Both final-encode with Daxur-Daemon's exact `compress.ts` settings: `libx265 -crf 28 -preset medium -tag:v hvc1 -pix_fmt yuv420p`, `aac 128k`.
- See ADR-009 for the original architecture and why node-canvas/sharp were ruled out for the legacy path; see ADR-012 for why the Playwright path became canonical and why the legacy path wasn't deleted.
- Known gaps: the timeline math is now a third copy alongside `player.js`/`ReplayPlayerComponent` (same duplication-maintenance risk already flagged for those two — see ADR-004) — and per ADR-012, the legacy Pillow renderer can now also silently drift from what the live canvas actually draws, since nothing enforces the two pipelines staying in visual sync; narration-overlap handling in the audio mix is untested since no current scenario produces overlapping clips.

## Feature: TTS narration for replays — ✅ Done

- Generates spoken narration for replay sequences via a pluggable TTS provider — **Chatterbox** (local/free, self-hosted, default) or **ElevenLabs** (cloud/paid, just an API key, no local server or LAN setup needed) — selected via `TTS_PROVIDER=chatterbox|elevenlabs`. See ADR-013.
- Two variants per event: a short version (concise) and a long version (detailed walkthrough) — `narrationShort` / `narrationLong` text fields on each manifest event
- Audio is pre-generated and cached via `scripts/generate-narration.mjs` (not generated live in-browser) into `narrationAudioShort` / `narrationAudioLong` manifest fields
- Implemented in both `replay/player.js` and `replay-app`'s `ReplayPlayerComponent`; narration on/off/short/long is a dropdown in both players
- See ADR-004 for the timing-sync and playback-speed decisions
- Cached narration clips are compressed Ogg/Opus (`.ogg`), not WAV — both providers encode Opus natively (Chatterbox via its OpenAI-compatible endpoint, ElevenLabs via `output_format=opus_48000_64`), so no transcode step is needed either way. See ADR-008 (Chatterbox) and ADR-013 (ElevenLabs).

### Timing sync — resolved

- Per step, duration = whichever is longer (visual action vs narration audio) — an extra hold phase is appended after the visual action if narration runs longer, so playback always waits for both before advancing
- Playback speed (0.5x–2x) applies uniformly to narration audio via `playbackRate`, matching the visual timeline; this is not pitch-corrected (see ADR-004 for why that's an acceptable tradeoff here)

## Feature: Seeded deterministic cursor noise — ✅ Done

- Optional numeric `seed` field on the manifest seeds a small deterministic PRNG (mulberry32, no new dependency)
- Adds small wobble to bezier mouse-move control points and circle-gesture radius/angle, so replays don't look perfectly robotic

## Feature: `asyncWait` action (time-compressed long waits) — 🔧 Prototyped, unverified live

- **Superseded in part by ADR-010 (video-first pivot): the region-crop compositing design described throughout this entry (`regionRect`, `captureAsyncRegionWait()`, the bounding-box-drift and element-resize risks below) has been removed from the codebase.** `AsyncWaitAction` now uses plain full-screen `frames` (same shape as `ScrollAction.frames`), matching how the video-export pipeline (ADR-009) and both live players now actually behave. This section is kept as-is below for historical record per house ADR-amendment practice — see ADR-010 for what changed and why, and for the full-frame export verification (23,258 bytes / 3.6s on a synthetic asyncWait scenario).
- **Extended by ADR-011: per-action `maxDisplayMs` cap and an optional "sped up `NNx`" badge.** `AsyncWaitAction` gained `maxDisplayMs?`/`speedupIndicator?`/`speedupIndicatorCorner?` — an authoring-time ceiling on how long one specific wait may occupy on screen (clamped into `frameDurationMs` at capture time by `CaptureSession.addAsyncWait()`, so no downstream consumer needed changes for the cap itself), plus an on-by-default badge rendered by both live players and the video-export rasterizer whenever real compression is happening (`realDurationMs > frameDurationMs`). See ADR-011 for the full design, defaults, and verification (including rendered example frames).
- Problem: long async waits (e.g. a 30-50s loading spinner/progress bar) shouldn't be skipped entirely (reads as fake/instant) or shown at real duration (dead air) — stop-motion-ui captures sparse screenshots, not video, so this needs time-compression, not a "skip video segment" mechanism
- **What's now actually built** (capture + manifest + both replay players), combining the original `asyncWait` idea below with the region-crop compositing idea from `docs/open-questions.md` and the same low/full-quality split already used for animated scroll frames:
  - **Manifest**: new `AsyncWaitAction` type in `shared/manifest-types.ts` (not a field bolted onto an existing type) — `regionRect` (the captured crop's bounding box, measured once), `frames` (ordered region-cropped — not full-screen — screenshots), `realDurationMs` (informational), `frameDurationMs` (required; the compressed replay duration). `screenshotRef` (inherited from `BaseEvent`) is the static full-screen base frame the crops get composited onto, captured once at the very start of the wait, reused from the triggering click's own screenshot. `CaptureSession.addAsyncWait()` wires it into the existing capture-session API alongside `addClick`/`addCircle`/`addScroll`.
  - **Capture**: `captureAsyncRegionWait()` in `capture/playwright/src/capture-demo.ts` polls `page.screenshot({ clip })` scoped to the region's bounding box (Playwright's `clip` option — confirmed via the installed package's type definitions; `locator.screenshot()` was considered but `clip` was preferred since the page is already scrolled into position) every `ASYNC_REGION_SAMPLE_MS` (400ms) until an app-level idle signal flips, with no upfront guess at the real duration — implementing the "oversample continuously, then downsample once real duration is known" idea below for the first time. `downsampleEvenly()` then picks `ASYNC_REGION_MAX_FRAMES` (6) evenly-spaced frames from however many were collected. Quality split mirrors `SCROLL_FRAME_QUALITY`: every frame except the last is saved at `ASYNC_REGION_FRAME_QUALITY` (20, low — each is only ever on screen for a slice of the compressed hold); the last is full ADR-003 quality (80, since it's the frame that actually lingers, including any narration overrun).
  - **Replay**: both `replay/player.js` and `replay-app`'s `ReplayPlayerComponent` got a new `'asyncWait'` phase kind, parallel to how `'circle'` loops an orbit over one static screenshot or (Angular-only) `'scroll'` cycles full-screen backgrounds — this is a third variant: small composited crops layered over a held static base. `sampleAt()` picks a frame index from `frac`/`frames.length` (cursor stays parked — no motion, mirroring `'scroll'`'s reasoning); `render()` draws the base frame as usual, then an extra `ctx.drawImage(cropImg, regionRect.x, regionRect.y)` on top, at the crop's own natural pixel size (not stretched to `regionRect`'s recorded width/height, so a stale rect mispositions rather than distorts the crop). Both players' `loadScenario()`/image-preload step were extended to also fetch each `AsyncWaitAction.frames[]` entry, the same way animated-scroll frames already were.
  - **Built specifically for the loading-bar use case, not async actions in general** (per explicit scope direction) — the concrete target is the Kitchen Sink demo's `[data-testid="kitchen-sink-async-active"]` container (a determinate `mat-progress-bar` + indeterminate `mat-progress-spinner` + status text, confirmed via the component source to have a stable, non-reflowing bounding box for the page's lifetime), wired into `capture-demo.ts`'s existing step 11.
  - **Architectural fix found and applied along the way**: `AsyncWaitAction.timestamp` is recorded *after* the real wait already elapsed (same as every other `CaptureSession.add*()` method), so the gap between it and the previous event's timestamp is the *entire real wait duration* — tens of seconds. Both players' `buildTimeline()` compute a move-glide phase from that gap for every other event type; left unhandled, this would have silently reintroduced exactly the "dead air" this feature exists to fix, just shifted one phase earlier (a multi-second-to-tens-of-seconds cursor glide immediately *before* the new compressed-wait phase, instead of during it). Fixed by special-casing `ev.type === 'asyncWait'` in both `buildTimeline()`s to skip/zero that glide — there's nothing to glide toward anyway, since the wait's cursor position is reused verbatim from the triggering click.
  - **Not run against a live browser.** This sandbox can't download a Chromium binary (network allowlist blocks `cdn.playwright.dev`) and has no system-installed browser, so none of the capture-side or replay-side code above has been executed end-to-end — only verified by reading Playwright's installed type definitions (to confirm the `clip` API surface) and by careful manual re-reading of every edited file (brace/logic structure, not a compiler or test run). Needs a real capture run + real replay viewing, on a machine that can launch a browser, before this is trusted in practice.
- Original mechanism (superseded by the above, kept for history): sample a handful of screenshots across the real wait window at a fixed interval (e.g. every 1-2s, capped ~4-6 frames), plus metadata for the real elapsed duration
- Refined sampling approach (now implemented — see `captureAsyncRegionWait()` above): the fixed-interval idea requires guessing the wait's real duration upfront, which is fragile. Capturing continuously and downsampling after the real duration is known only makes sense paired with region-scoped capture — oversampling a tiny cropped region is cheap per-frame; oversampling full-screen screenshots at the same frequency would not be. (Connection from `docs/open-questions.md`'s "Element-region screenshot compositing" entry, now resolved into a real implementation for this one case.)
- On replay: cycles through the captured frames for a compressed display duration instead of waiting the real duration, conceptually reusing the "loop frames over a phase duration" mechanic already built for circle-gesture orbit phases — see "Replay" above for the actual new phase kind.
- Tuning knob: `ASYNC_REGION_DISPLAY_MS` (currently 2500ms) is the compressed display duration; `ASYNC_REGION_MAX_FRAMES` (6) and `ASYNC_REGION_SAMPLE_MS` (400ms) control sampling density/cost.
- Narration interaction: existing "whichever is longer" timing-sync (visual hold vs narration duration, speed-adjusted — see ADR-004) applies here too — the new `'asyncWait'` phase is wired in as a valid narration owner in both players, same as `'move'`/`'circle'`/`'scroll'`.
- Flag: the demo-readiness-checklist's "ready/idle signal" pattern is normally used to know when it's *safe to skip* a wait — for `asyncWait` capture it's used differently, to mark the real start/end of the loading window so the capture tool knows where to sample frames within it, not to skip past it. Worth adding as a nuance to that skill's docs later; not edited yet.
- Reference fixture: `replay-app`'s Kitchen Sink page (`replay-app/src/app/kitchen-sink/`, nav tab `nav-kitchen-sink`) — a ~40s async action (configurable via `?asyncDurationMs=`/`?fastAsync=1`) paired with a determinate mat-progress-bar and a mat-progress-spinner, now captured via the mechanism above in `capture/playwright/src/capture-demo.ts` (step 11).
- **Real, currently undocumented-elsewhere risk: bounding-box drift.** `regionRect` is measured exactly once (`region.boundingBox()`, right when the wait starts) and never re-measured for the rest of the wait. If the page reflows mid-wait — something elsewhere on the page shifts the loading region's position, or the region itself resizes — every frame captured after that point is still clipped from the *stale* rect, and replay composites it at that same stale `(x, y)`. Nothing in the capture or replay code detects this; it would silently produce a crop that's subtly (or badly) misaligned with the actual element underneath. The Kitchen Sink fixture's `.ks-async-indicators` container was specifically chosen because its CSS (`flex column`, fixed children) makes this unlikely *for that one fixture*, but this is a fixture-specific mitigation, not a structural fix — any future region scoped to a less stable container would hit this for real. A real fix would need either periodic re-measurement during the wait (extra cost, partially defeating the "cheap because oversampling a fixed small crop is cheap" argument) or an explicit "this region's box is assumed stable" precondition documented per call site.
- **Real, separate risk: element resize.** Distinct from drift (position shifting) — if the region's *size* changes mid-wait (e.g. the status text wraps to a second line, growing the container), later raw frames would naturally vary in pixel dimensions, and `downsampleEvenly()`/render()'s draw-at-natural-size approach would just show that size change directly rather than crashing, but it'd look like an inconsistent flicker in the crop's footprint since `regionRect`'s recorded size no longer matches every frame. Not handled or mitigated; also not exercised by the Kitchen Sink fixture, since its container's children have fixed/predictable sizing for the demo's duration.
- Status: prototyped end-to-end (capture → manifest → both replay players), not live-verified — see disclosure above

## Feature: `type` action (text input animation) — 💡 Proposed, not built

- Problem: a click→type→screenshot sequence currently jumps straight from empty to final text value at the next screenshot — no animation in between, unlike mouse movement which eases naturally across gaps via the bezier cursor logic. Typing into a form field is common enough in real UIs that this gap matters for demo realism
- Mechanism: new manifest action type `type`
- Two possible implementation approaches — **open design decision, not yet picked**:
  1. **Synthesized typing** — no extra screenshots needed. Render the target text character-by-character (or small chunks) directly in the replay canvas over the input element's known bounding box, with seeded variable cadence reusing the existing mulberry32 PRNG pattern (same as mouse wobble) so typing speed has natural human-like variance instead of robotic uniform timing. Cheap, zero extra capture cost; fidelity depends on matching the input's font/styling closely enough that the overlay looks native rather than pasted on top
  2. **Real partial element captures** — capture a handful of cropped screenshots of just the input's bounding box at intervals while typing (not full-screen), then composite those onto the base screenshot during replay. A strong concrete use case for the element-region screenshot compositing idea in `docs/open-questions.md` — typing is arguably a better fit than the loading-spinner case that idea was originally floated for, since the input region is small, well-defined, and (unlike a spinner during a loading state) isn't at risk of unrelated layout reflow shifting it mid-action
- Reference fixture: the same Kitchen Sink page (`replay-app/src/app/kitchen-sink/`) also covers this — a plain text input and a textarea, both filled via Playwright's `.fill()` in `capture/playwright/src/capture-demo.ts` (steps 8-9), which jumps straight from empty to final value with no intermediate frames. Use this fixture to compare approach (1) vs (2) above once one is picked.
- Status: idea/proposed, not yet built; implementation approach (1) vs (2) above still open

## Feature: "scroll showcase" gesture (deliberate presentational scroll) — ✅ Done

- Problem: the existing circle-gesture action lets a captured action deliberately draw attention to something ("look here"), distinct from incidental cursor movement. There's no analogous deliberate gesture for scrolling — scrolling up/down through a page specifically to show its content as part of a demo is a different need than just repositioning before a click
- Built on top of the basic `scroll` action (snap-to-position, fixes the click-misalignment bug — see that entry's history above), as an optional `frames` array on `ScrollAction` (`shared/manifest-types.ts`) — `screenshotRef` stays the single representative/last frame so older single-snap manifests are unaffected
- Follow-up fix (non-animated scrolls only): the original snap-to-position fix above was an instant cut to the post-scroll background with the cursor pre-parked at its destination — that fixed the misalignment bug but introduced a visible cursor teleport whenever a scroll preceded the next interaction (reported: cursor jumping straight from one step to the next with no motion in between, e.g. an async-result callout straight to a dialog-open click). `replay-player.component.ts`'s `buildTimeline()` now gives non-animated `'scroll'` events a real glide (`MovePhase`) instead of a static snap, rendered over the already-correct post-scroll screenshot — keeps the misalignment fix while restoring visible cursor motion. Animated scrolls (the `frames` case just above) are unaffected: the cursor staying parked there is intentional since the *background* itself conveys the motion.
- Mechanism actually implemented: rather than the oversample-then-downsample technique sketched below for `asyncWait` (needed there because the real wait duration isn't known upfront), `scrollToAndRecord()` in `capture/playwright/src/capture-demo.ts` resolves the page's real, clamped scroll target first, then sets `frameCount` evenly-spaced *absolute* `window.scrollTo()` positions between the real start and real end (default 12 frames, opt in via `{ animated: true }`) and captures one frame per step
  - Fixed a real bug found via a live capture: an earlier version split the requested `deltaY` into N *relative* wheel-delta ticks instead of resolving the real target first. `deltaY` is just a guessed/requested amount, not the page's actual remaining scroll room, and routinely overshoots it — when it does, real motion front-loads into however many ticks it takes to hit the page's true max scroll, and every remaining tick becomes a silent no-op. Confirmed via `md5sum` across a real capture: one scroll site produced ~20 of 24 byte-identical frames at the end, another (where the page was already at max scroll before the call even started) produced all 24 identical. Resolving the clamped target up front and interpolating absolute positions fixes this regardless of how `deltaY` compares to the page's real room
  - Stale-screenshot question (raised after the frame-count default was lowered from 24 to 12): not an issue. `capture-demo.ts`'s `main()` deletes and recreates both the staging dir and the final `replay-app/public/test-scenarios/demo-gallery/` output dir on every run (`rmSync(..., { recursive: true, force: true })` before each), so a smaller frame count on a later run can never leave extra frames behind from an earlier, larger-frame-count run
- Replay: `replay-player.component.ts` adds a new `ScrollPhase` (cursor parked, background cycles through `frames` via `sampleAt()`'s 'scroll' branch) instead of reusing `ShowPhase`'s single-screenshot snap — animates smoothly across a duration that, by default, scales with frame count (`SCROLL_ANIM_MS_PER_FRAME`, clamped to `[SCROLL_ANIM_MIN_MS, SCROLL_ANIM_MAX_MS]`), conceptually similar to how the circle gesture loops through its orbit phase but without reusing that exact phase type (circle orbits a cursor over one static screenshot; this cycles screenshots with a static cursor — different enough axis that a new phase type was cleaner than overloading either existing one)
  - Optional explicit duration: `ScrollAction.frameDurationMs` (set via `scrollToAndRecord()`'s `opts.durationMs`, e.g. `{ animated: true, frameCount: 12, durationMs: 750 }` for "12 frames over 0.75s") lets a capture call site pin the exact replay duration instead of relying on the frame-count-based default — `buildTimeline()` prefers it when present (sanity-clamped to `[SCROLL_ANIM_EXPLICIT_MIN_MS, SCROLL_ANIM_EXPLICIT_MAX_MS]`), falling back to the frame-count estimate otherwise, so older/duration-less manifests are unaffected
- Demo fixture: opted in on the Kitchen Sink page's mat-select and async-trigger scrolls (`capture/playwright/src/capture-demo.ts`, steps 10-11) as the two test sites — a real capture confirmed both have substantial real scroll room (700px and ~487px respectively). The async-trigger site also doubles as the test case for explicit `durationMs` (pinned to 750ms). The dialog-trigger and bottom-marker scrolls (steps 12-13) are deliberately left on the default single-snap behavior: a real capture showed both have negligible-to-zero real room left by that point in the page (the earlier scrolls already used up most/all of it), so animating them would just spend frames showing a near-static or fully static scroll
- Status: done; toggle is per-call-site via `scrollToAndRecord()`'s `{ animated: true }` (optionally `{ animated: true, frameCount: N }` to override the default of 12, and/or `{ durationMs: N }` to pin the exact replay duration instead of the frame-count-based default)

### Storage efficiency: tall-strip + virtual camera pan vs discrete frames — idea, not built

- Core insight: for scrolling specifically, there's a cheaper alternative to the discrete `frameCount`-frame capture above — a single "tall strip" screenshot plus a virtual camera pan during replay, **if** page content is static during the scroll
- Naive approach (don't do this): capture one screenshot covering the page's *entire* scrollable height regardless of how far the interaction actually scrolled — wasteful on a very tall page (e.g. 10,000px) when the interaction only moves 200px; most of the captured image is never shown
- Better approach: capture one screenshot scoped only to the *actually visited scroll range* — from min to max scroll position reached, plus one viewport height of margin. Height ≈ `V + S` (V = viewport height, S = distance actually scrolled). Stays cheap on tall pages since it only captures what was visited, not the whole document
- Replay: animate a viewport-sized "virtual camera window" sliding continuously down/up across that one tall-strip image — smooth scroll motion from a single image, no frame count needed
- Cost comparison vs the discrete N-frame approach above (N=12 default, raw pixel cost ≈ `N × V`): tall-strip (`≈ V + S`) is cheaper whenever `S < (N-1) × V` — i.e. unless one scroll gesture covers more than ~11 screens (N=12), which essentially never happens in a real demo. So tall-strip beats discrete frames on storage for virtually all realistic scroll distances, and gives continuous motion instead of discrete frame jumps
- Caveat/condition: only valid when page content is static during the scroll — only what's *in view* changes, not the content itself. If something inside the viewport changes independent of scroll position (lazy-loading list populating, animated sticky header, autoplaying video, live counter), a single static strip can't represent that — falls back to the discrete N-frame approach above
  - Further-out idea, not to be designed now: a hybrid — tall-strip for the static base, discrete frames layered on top for the dynamic regions (would also lean on the element-region compositing idea in `docs/open-questions.md`)

## Feature: Root-level CLI consolidation — ✅ Done (see ADR-012)

## Maintenance note: `replay/player.js` deprecation started

- `replay/player.js` (the vanilla JS/Canvas player) now carries an explicit deprecation notice in its header pointing at `replay-app`'s `ReplayPlayerComponent` as the maintained player. It is **not yet removed** — it still works and has no build step, so it's kept as a fallback, but it will not necessarily receive new features going forward. It has already drifted: it does not implement the ADR-011 `maxDisplayMs`/sped-up-indicator badge, since that work only touched the Angular component and the export pipeline.
- README's "Replay player" status entries still describe `replay/player.js` as co-equal to the Angular wrapper ("an alternative, not a replacement") — that framing is now stale and should be revisited once a decision is made on whether/when to actually remove the vanilla player, not just deprecate it.
- Recommendation: default to tall-strip + camera-pan for scroll showcases on pages with static content during scroll (the common case); reserve discrete frame-sampling (already built above) for scrolls where content changes mid-gesture, which should be rare — flag as a follow-up refinement, not yet built
