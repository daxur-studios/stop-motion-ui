# Roadmap / Future Ideas

## Feature: TTS narration for replays — ✅ Done

- Uses Daxur Daemon's local TTS capability (Chatterbox TTS) to generate spoken narration for replay sequences
- Two variants per event: a short version (concise) and a long version (detailed walkthrough) — `narrationShort` / `narrationLong` text fields on each manifest event
- Audio is pre-generated and cached via `scripts/generate-narration.mjs` (not generated live in-browser) into `narrationAudioShort` / `narrationAudioLong` manifest fields
- Implemented in both `replay/player.js` and `replay-app`'s `ReplayPlayerComponent`; narration on/off/short/long is a dropdown in both players
- See ADR-004 for the timing-sync and playback-speed decisions
- Cached narration clips are compressed Ogg/Opus (`.ogg`), not WAV — Chatterbox's OpenAI-compatible endpoint encodes Opus natively server-side, so no transcode step was needed. See ADR-008

### Timing sync — resolved

- Per step, duration = whichever is longer (visual action vs narration audio) — an extra hold phase is appended after the visual action if narration runs longer, so playback always waits for both before advancing
- Playback speed (0.5x–2x) applies uniformly to narration audio via `playbackRate`, matching the visual timeline; this is not pitch-corrected (see ADR-004 for why that's an acceptable tradeoff here)

## Feature: Seeded deterministic cursor noise — ✅ Done

- Optional numeric `seed` field on the manifest seeds a small deterministic PRNG (mulberry32, no new dependency)
- Adds small wobble to bezier mouse-move control points and circle-gesture radius/angle, so replays don't look perfectly robotic
- Same seed + same manifest always reproduces the same wobble (no `Math.random()`); cursor still arrives at the exact intended coordinates every time
- Implemented identically in both `replay/player.js` and `replay-app`'s `ReplayPlayerComponent`
- See ADR-004 for the algorithm choice and jitter-envelope design

## Feature: `asyncWait` action (time-compressed long waits) — 💡 Proposed, not built

- Problem: long async waits (e.g. a 30-50s loading spinner/progress bar) shouldn't be skipped entirely (reads as fake/instant) or shown at real duration (dead air) — stop-motion-ui captures sparse screenshots, not video, so this needs time-compression, not a "skip video segment" mechanism
- Mechanism: new manifest action type `asyncWait` — during real capture, sample a handful of screenshots across the real wait window (e.g. every 1-2s, capped ~4-6 frames — enough to convey motion like a spinning spinner or advancing progress bar), plus metadata for the real elapsed duration
- Refined sampling approach (preferred over the fixed-interval idea above): the original mechanism requires picking a sampling interval upfront, which means guessing or knowing the wait's real duration in advance — fragile since real wait durations vary. Instead, capture continuously (or at high frequency) for the entire real wait with no upfront duration assumption, then once the wait actually finishes and the real elapsed duration is known, downsample after the fact — keep a small number of evenly-spaced frames (~4-6, same cap as above) and discard the rest
  - This oversample-then-downsample technique only makes sense paired with region-scoped capture (see "Element-region screenshot compositing" in `docs/open-questions.md`), not full-screen capture — oversampling a tiny cropped region (e.g. a spinner) at high frequency is cheap per-frame, so capturing far more than needed and discarding most is affordable; oversampling full-screen screenshots at the same frequency would not be
  - Still proposed, not built — this refines the sampling strategy above, doesn't replace the rest of the mechanism
- On replay: cycle through the captured frames for a compressed display duration instead of waiting the real duration — reuses the existing "loop frames over a phase duration" mechanic already built for circle-gesture orbit phases in `replay/player.js`; no new playback logic needed
- Tuning knob: configurable display-duration cap per `asyncWait` event — sensible default ~2-4s, floor ~1s (below this reads as a glitch), ceiling ~4s (above this drags) — this is the quick-vs-realistic balance
- Narration interaction: existing "whichever is longer" timing-sync (visual hold vs narration duration, speed-adjusted — see ADR-004) applies here too, same pattern as other steps
- Demo app implication: `replay-app` Demo Gallery needs a second page/route with a deliberately slow flow (button → 30-50s spinner/progress bar → result), specifically as a test fixture for this feature once built
- Flag: the demo-readiness-checklist's "ready/idle signal" pattern is normally used to know when it's *safe to skip* a wait — for `asyncWait` capture it's used differently, to mark the real start/end of the loading window so the capture tool knows where to sample frames within it, not to skip past it. Worth adding as a nuance to that skill's docs later; not edited yet.
- Reference fixture: `replay-app`'s Kitchen Sink page (`replay-app/src/app/kitchen-sink/`, nav tab `nav-kitchen-sink`) now exists for this — a ~40s async action (configurable via `?asyncDurationMs=`/`?fastAsync=1`) paired with a determinate mat-progress-bar and a mat-progress-spinner, captured as-is by `capture/playwright/src/capture-demo.ts` (step 11). Today's capture has no compression for this wait, so replaying it currently shows the real-time dead air this feature is meant to fix — see code comments on that step for the exact mechanism.
- Status: idea/proposed, not yet built

## Feature: `type` action (text input animation) — 💡 Proposed, not built

- Problem: a click→type→screenshot sequence currently jumps straight from empty to final text value at the next screenshot — no animation in between, unlike mouse movement which eases naturally across gaps via the bezier cursor logic. Typing into a form field is common enough in real UIs that this gap matters for demo realism
- Mechanism: new manifest action type `type`
- Two possible implementation approaches — **open design decision, not yet picked**:
  1. **Synthesized typing** — no extra screenshots needed. Render the target text character-by-character (or small chunks) directly in the replay canvas over the input element's known bounding box, with seeded variable cadence reusing the existing mulberry32 PRNG pattern (same as mouse wobble) so typing speed has natural human-like variance instead of robotic uniform timing. Cheap, zero extra capture cost; fidelity depends on matching the input's font/styling closely enough that the overlay looks native rather than pasted on top
  2. **Real partial element captures** — capture a handful of cropped screenshots of just the input's bounding box at intervals while typing (not full-screen), then composite those onto the base screenshot during replay. A strong concrete use case for the element-region screenshot compositing idea in `docs/open-questions.md` — typing is arguably a better fit than the loading-spinner case that idea was originally floated for, since the input region is small, well-defined, and (unlike a spinner during a loading state) isn't at risk of unrelated layout reflow shifting it mid-action
- Reference fixture: the same Kitchen Sink page (`replay-app/src/app/kitchen-sink/`) also covers this — a plain text input and a textarea, both filled via Playwright's `.fill()` in `capture/playwright/src/capture-demo.ts` (steps 8-9), which jumps straight from empty to final value with no intermediate frames. Use this fixture to compare approach (1) vs (2) above once one is picked.
- Status: idea/proposed, not yet built; implementation approach (1) vs (2) above still open

## Feature: "scroll showcase" gesture (deliberate presentational scroll) — ✅ Done

- Problem: the existing circle-gesture action lets a captured action deliberately draw attention to something ("look here"), distinct from incidental cursor movement. There's no analogous deliberate gesture for scrolling — scrolling up/down through a page specifically to show its content as part of a demo is a different need than just repositioning before a click
- Built on top of the basic `scroll` action (snap-to-position, fixes the click-misalignment bug — see that entry's history above), as an optional `frames` array on `ScrollAction` (`shared/manifest-types.ts`) — `screenshotRef` stays the single representative/last frame so older single-snap manifests are unaffected
- Follow-up fix (non-animated scrolls only): the original snap-to-position fix above was an instant cut to the post-scroll background with the cursor pre-parked at its destination — that fixed the misalignment bug but introduced a visible cursor teleport whenever a scroll preceded the next interaction (reported: cursor jumping straight from one step to the next with no motion in between, e.g. an async-result callout straight to a dialog-open click). `replay-player.component.ts`'s `buildTimeline()` now gives non-animated `'scroll'` events a real glide (`MovePhase`) instead of a static snap, rendered over the already-correct post-scroll screenshot — keeps the misalignment fix while restoring visible cursor motion. Animated scrolls (the `frames` case just above) are unaffected: the cursor staying parked there is intentional since the *background* itself conveys the motion.
- Mechanism actually implemented: rather than the oversample-then-downsample technique sketched below for `asyncWait` (needed there because the real wait duration isn't known upfront), `scrollToAndRecord()` in `capture/playwright/src/capture-demo.ts` resolves the page's real, clamped scroll target first, then sets `frameCount` evenly-spaced *absolute* `window.scrollTo()` positions between the real start and real end (default 12 frames, opt in via `{ animated: true }`) and captures one frame per step
  - Fixed a real bug found via a live capture: an earlier version split the requested `deltaY` into N *relative* wheel-delta ticks instead of resolving the real target first. `deltaY` is just a guessed/requested amount, not the page's actual remaining scroll room, and routinely overshoots it — when it does, real motion front-loads into however many ticks it takes to hit the page's true max scroll, and every remaining tick becomes a silent no-op. Confirmed via `md5sum` across a real capture: one scroll site produced ~20 of 24 byte-identical frames at the end, another (where the page was already at max scroll before the call even started) produced all 24 identical. Resolving the clamped target up front and interpolating absolute positions fixes this regardless of how `deltaY` compares to the page's real room
  - Stale-screenshot question (raised after the frame-count default was lowered from 24 to 12): not an issue. `capture-demo.ts`'s `main()` deletes and recreates both the staging dir and the final `replay-app/public/test-scenarios/demo-gallery/` output dir on every run (`rmSync(..., { recursive: true, force: true })` before each), so a smaller frame count on a later run can never leave extra frames behind from an earlier, larger-frame-count run
- Replay: `replay-player.component.ts` adds a new `ScrollPhase` (cursor parked, background cycles through `frames` via `sampleAt()`'s 'scroll' branch) instead of reusing `ShowPhase`'s single-screenshot snap — animates smoothly across a duration that, by default, scales with frame count (`SCROLL_ANIM_MS_PER_FRAME`, clamped to `[SCROLL_ANIM_MIN_MS, SCROLL_ANIM_MAX_MS]`), conceptually similar to how the circle gesture loops through its orbit phase but without reusing that exact phase type (circle orbits a cursor over one static screenshot; this cycles screenshots with a static cursor — different enough axis that a new phase type was cleaner than overloading either existing one)
  - Optional explicit duration: `ScrollAction.frameDurationMs` (set via `scrollToAndRecord()`'s `opts.durationMs`, e.g. `{ animated: true, frameCount: 12, durationMs: 750 }` for "12 frames over 0.75s") lets a capture call site pin the exact replay duration instead of relying on the frame-count-based default — `buildTimeline()` prefers it when present (sanity-clamped to `[SCROLL_ANIM_EXPLICIT_MIN_MS, SCROLL_ANIM_EXPLICIT_MAX_MS]`), falling back to the frame-count estimate otherwise, so older/duration-less manifests are unaffected
- Demo fixture: opted in on the Kitchen Sink page's mat-select and async-trigger scrolls (`capture/playwright/src/capture-demo.ts`, steps 10-11) as the two test sites — a real capture confirmed both have substantial real scroll room (700px and ~487px respectively). The async-trigger site also doubles as the test case for explicit `durationMs` (pinned to 750ms). The dialog-trigger and bottom-marker scrolls (steps 12-13) are deliberately left on the default single-snap behavior: a real capture showed both have negligible-to-zero real room left by that point in the page (the earlier scrolls already used up most/all of it), so animating them would just spend frames showing a near-static or fully static scroll
- Status: done; toggle is per-call-site via `scrollToAndRecord()`'s `{ animated: true }` (optionally `{ animated: true, frameCount: N }` to override the default of 12, and/or `{ durationMs: N }` to pin the exact replay duration instead of the frame-count-based default)

### Storage efficiency: tall-strip + virtual camera pan vs discrete frames — idea, not built

- Core insight: for scrolling specifically, there's a cheaper alternative to the discrete `frameCount`-frame capture above — a single "tall strip" screenshot plus a virtual camera pan during replay, **if** page content is static during the scroll
- Naive approach (don't do this): capture one screenshot covering the page's *entire* scrollable height regardless of how far the interaction actually scrolled — wasteful on a very tall page (e.g. 10,000px) when the interaction only moves 200px; most of the captured image is never shown
- Better approach: capture one screenshot scoped only to the *actually visited scroll range* — from min to max scroll position reached, plus one viewport height of margin. Height ≈ `V + S` (V = viewport height, S = distance actually scrolled). Stays cheap on tall pages since it only captures what was visited, not the whole document
- Replay: animate a viewport-sized "virtual camera window" sliding continuously down/up across that one tall-strip image — smooth scroll motion from a single image, no frame count needed
- Cost comparison vs the discrete N-frame approach above (N=12 default, raw pixel cost ≈ `N × V`): tall-strip (`≈ V + S`) is cheaper whenever `S < (N-1) × V` — i.e. unless one scroll gesture covers more than ~11 screens (N=12), which essentially never happens in a real demo. So tall-strip beats discrete frames on storage for virtually all realistic scroll distances, and gives continuous motion instead of discrete frame jumps
- Caveat/condition: only valid when page content is static during the scroll — only what's *in view* changes, not the content itself. If something inside the viewport changes independent of scroll position (lazy-loading list populating, animated sticky header, autoplaying video, live counter), a single static strip can't represent that — falls back to the discrete N-frame approach above
  - Further-out idea, not to be designed now: a hybrid — tall-strip for the static base, discrete frames layered on top for the dynamic regions (would also lean on the element-region compositing idea in `docs/open-questions.md`)
- Recommendation: default to tall-strip + camera-pan for scroll showcases on pages with static content during scroll (the common case); reserve discrete frame-sampling (already built above) for scrolls where content changes mid-gesture, which should be rare — flag as a follow-up refinement, not yet built
