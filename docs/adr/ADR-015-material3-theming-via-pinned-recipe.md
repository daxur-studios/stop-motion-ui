# ADR-015: Angular Material 3 theming via the `angular-firebase-20` pinned recipe

**Status:** Accepted

**Context:**

`replay-app` looked visibly broken: a dark, hand-coded app shell (`body { background: #111; color: #eee; }` plus per-component hex grays in `app.scss`, `kitchen-sink.component.scss`, `demo-gallery.component.scss`, `replay-player.component.scss`, and the new `settings.component.scss`) sitting on top of `@import '@angular/material/prebuilt-themes/indigo-pink.css'` — a fixed **light** Material 2 theme. Every Material component (`mat-select`, `mat-form-field`/`mat-input`, `mat-radio-group`, `mat-progress-bar`/`mat-progress-spinner`) rendered with light-theme chrome — white backgrounds, dark-on-light text — inside an otherwise dark page. This was most visible on the new Settings panel (ADR-014), which is almost entirely Material form controls, but the same prebuilt-theme import affected every page.

Separately, this user's own scaffolding tool, `Daxur-Daemon`, already defines a prescriptive theming convention for new Angular apps: `cli/src/scaffold/recipes/angular-firebase-20/AGENT.md`. It mandates Angular Material 3 via the `mat.theme()` Sass API, a `src/app/theme/` folder with four specific files, and — explicitly — **copying those files verbatim from a pinned, SHA-locked reference repo** rather than hand-rolling palettes or tokens ("do not invent ad-hoc `theme.scss` tokens").

**Decision:**

- Adopted the recipe's theme structure under `replay-app/src/app/theme/`:
  - `theme.scss` — `@use '@angular/material' as mat; @include mat.core();` plus light/dark `mat.theme(...)` blocks scoped to `html`/`html.app-light-theme`/`html.app-dark-theme`.
  - `_theme-colors.scss` — the M3 palette, copied verbatim from the pin (not regenerated locally, since no `ng generate @angular/material:theme-color` run was needed — the pinned palette was reused as-is).
  - `snackbar.scss` — `MatSnackBar` panel CSS variables, copied verbatim. Not yet used anywhere in `replay-app` (no `MatSnackBar` call sites), kept for parity with the recipe's file set.
  - `theme.service.ts` — toggles `app-light-theme`/`app-dark-theme` on `<html>`, persists to `localStorage`, respects `prefers-color-scheme`. **One deliberate deviation from the pin:** the final fallback (no stored preference, no system preference signal) defaults to `'dark'` instead of `'light'`, since this app's entire existing UI was built dark-only — defaulting new visitors to light would have reintroduced the exact mismatch this change fixes.
  - All four copied from `meowney (sibling project)` at the pinned commit `b7cb672c1a0c0ee8aaef22b97823fb4b7bc81f7c` (extracted via `git show <SHA>:<path>`, since meowney's working tree has since moved past that commit).
- `src/styles.scss` now `@use`s `app/theme/theme.scss` instead of importing `indigo-pink.css`. The CDK overlay structural CSS import (`@angular/cdk/overlay-prebuilt.css`) stays, since that's purely positioning/structural, not a color theme.
- Root `App` component (`app.ts`) now `inject(ThemeService)`s so the theme class is applied to `<html>` before first paint.
- `src/index.html` now loads Roboto + Material Symbols from Google Fonts, per the recipe's step 10 (previously no web font was loaded at all; Material's typography config in `theme.scss` specifies Roboto, so the font needs to actually be available).
- Every component SCSS file touched (`app.scss`, `settings.component.scss`, `kitchen-sink.component.scss`, `demo-gallery.component.scss`, `replay-player.component.scss`) had its hand-picked hex grays replaced with Material 3 system tokens (`--mat-sys-surface-container`, `--mat-sys-on-surface-variant`, `--mat-sys-outline`, etc.), so custom chrome (nav links, cards, native `<input>`/`<button>`/`<select>` elements not using Material form-field components) tracks the same theme as the Material controls instead of being independently hardcoded. Two documented, deliberate exceptions were kept as literal colors rather than tokens: the replay canvas `#stage`/export-mode background (must stay pixel-stable black for Playwright screenshot export regardless of active theme) and `.settings-feedback-success`'s green (M3 doesn't define a "success" semantic role).
- This recipe's `app.config.ts`/Firebase-related steps (steps 2, 3, 5 of the AGENT.md) were **not** applied — `replay-app` has no Firebase dependency, and the user's own framing of this task scoped it to theming only.

**Consequences:**

- Material form controls and custom dark chrome now derive from the same token set, eliminating the light-inputs-in-a-dark-app mismatch across the whole app, not just Settings.
- This repo now has a `theme/` folder structurally identical (minus Firebase bits) to the user's other Angular projects scaffolded from `angular-firebase-20` (or its sibling recipes), making `replay-app` a consistent sibling rather than a one-off, which was the explicit goal.
- **This convention should be treated as the standard for all future UI work in this repo.** Any new component should use `--mat-sys-*` tokens for color, not new hardcoded hex values; any new Material 3 surface should rely on `theme.scss`'s existing `mat.theme()` blocks rather than a parallel theme setup.
- A light/dark toggle UI was **not** added — `ThemeService` already supports `toggle()`/`setLightMode()`/`setDarkMode()`, and the app currently just runs in dark mode by default (matching its prior fixed-dark aesthetic) with no way for a user to switch at runtime. Wiring a toggle into the nav is a natural, low-risk follow-up if light mode is ever wanted, but was out of scope here.
- **Verification performed:** `node_modules/.bin/ngc -p tsconfig.app.json --noEmit` (the Angular template compiler, strict-template-mode included) and `node_modules/.bin/tsc -p tsconfig.app.json --noEmit` both pass clean after this change. Every touched file was also independently checked for the disk-sync truncation bug seen repeatedly in earlier sessions in this repo (Write/Edit reporting success while bytes on disk were truncated mid-statement) — this recurred on nearly every file touched in this change (`app.ts`, `app.scss`, `styles.scss`, `index.html`, and all five touched component `.scss` files) and was fixed via the established bash-heredoc-rewrite-and-verify pattern; final byte-level checks (`wc -l`, `tail -c 1`, `tail -5`) confirm every file now ends cleanly.
- **Not verified:** no live browser render. There is no way to launch `ng serve`/a real browser in this sandbox (same `esbuild` platform-mismatch limitation noted in `docs/agent-maintainability.md` and ADR-013/ADR-014), so the actual rendered appearance — whether `mat-select`'s dropdown panel, `mat-radio-group`'s buttons, etc. visually look correct in dark mode — has only been verified by reading the generated `mat.theme()` Sass structure and confirming it matches the pinned reference, plus successful compilation. Treat this as "implemented, structurally verified, not visually confirmed" until someone runs `npm run dev` and opens the app (especially `/settings`) in a real browser.
