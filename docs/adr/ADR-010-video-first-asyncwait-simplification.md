# ADR-010: Video Is the Primary Deliverable; asyncWait Drops Region-Crop Compositing

**Status:** Accepted

**Context:** ADR-009 added a real headless video-export pipeline. Once that existed and was verified end-to-end, the priority ordering between the two output formats flipped: **video export is now the primary deliverable.** The live `<canvas>` player (`replay/player.js` and `replay-app`'s `ReplayPlayerComponent`) is downgraded to an internal debugging/preview tool — useful for iterating on a manifest before exporting, not something asset size needs to be optimized for anymore.

This matters concretely for the `asyncWait` action (see roadmap.md's "Feature: `asyncWait` action" entry and `docs/open-questions.md`'s "Element-region screenshot compositing" entry for the full prior history). The version built before this ADR captured one full-screen base screenshot plus a handful of small, region-cropped frames (`regionRect`-sized, not full-screen) layered on top of that base at replay time — `AsyncWaitAction.regionRect` recorded the crop's bounding box once at the start of the wait, and both players' `render()` did an extra `ctx.drawImage(cropImg, regionRect.x, regionRect.y)` after drawing the base screenshot. The entire point of that design was byte-savings for the live in-browser player: cropping let the oversample-then-downsample technique run cheaply against a tiny region instead of full frames.

That justification stops applying once video is the target:
- **h265 inter-frame compression already solves the asset-size problem.** "Mostly static page + one small moving region" (a progress bar, a spinner) is close to the textbook case inter-frame prediction is good at — successive full frames that mostly repeat the previous frame compress to a small delta automatically, no manual region-scoping needed.
- **Region-cropping was actively risky**, not just unnecessary. Roadmap.md documented two real, unmitigated risks with the old design: bounding-box drift (the cached `regionRect` going stale if the page reflows mid-wait, so a later frame's crop lands at the wrong position) and element resize (the crop's actual pixel size changing mid-wait while `regionRect`'s recorded size doesn't). Both are now moot — full-frame sampling makes a stale-position composite **structurally impossible**, since there is no base-frame-plus-overlay step left to drift apart. Every captured frame is a complete, self-contained screenshot.

**Decision:** Simplify `AsyncWaitAction` back down to plain full-screen frame sampling — the same shape `ScrollAction.frames` already uses — and remove the region-crop/bounding-box/compositing machinery entirely.

Concretely removed/changed:
- **`shared/manifest-types.ts`** — `AsyncWaitAction.regionRect` field deleted. `frames` is now documented as full-screen screenshots, not region crops. (Doc comment rewritten to point future readers at this ADR and at the now-historical write-up in `docs/open-questions.md`.)
- **`shared/capture-session.ts`** — `AddAsyncWaitArgs.regionRect` and the corresponding field in `addAsyncWait()`'s constructed event removed.
- **`capture/playwright/src/capture-demo.ts`** — `captureAsyncRegionWait()` renamed to `captureAsyncWait()`, its `region: Locator` parameter and `page.screenshot({ clip })` bounding-box logic removed (now plain `page.screenshot()`, full frame, every sample). Constants renamed to drop the now-inaccurate "region" framing: `ASYNC_REGION_FRAME_QUALITY` → `ASYNC_WAIT_FRAME_QUALITY`, `ASYNC_REGION_SAMPLE_MS` → `ASYNC_WAIT_SAMPLE_MS`, `ASYNC_REGION_MAX_FRAMES` → `ASYNC_WAIT_MAX_FRAMES`, `ASYNC_REGION_DISPLAY_MS` → `ASYNC_WAIT_DISPLAY_MS`.
- **`replay/player.js` and `replay-app/.../replay-player.component.ts`** — the asyncWait compositing block in `render()` (the extra `drawImage` after the base screenshot) removed entirely; `sampleAt()`'s asyncWait branch now swaps `screenshot` directly to the current cycling frame instead of returning a separate `region` object for `render()` to composite.
- **`scripts/build-frame-plan.mjs` and `scripts/render-frames.py`** (the ADR-009 video-export pipeline) — same two changes mirrored: `buildTimeline()`'s asyncWait phase no longer carries `regionRect`; `sampleAt()` swaps `screenshot` by frame index; `render-frames.py`'s `if frame["region"]: ...` compositing step removed, since `frame["region"]` no longer exists in `frame-plan.json` — the base screenshot lookup that already worked for `move`/`circle`/`scroll` phases now also covers `asyncWait` unchanged.

The oversample-then-downsample technique itself is **unchanged in spirit** — still poll continuously during the real wait, still downsample to an evenly-spaced, capped frame count once the real duration is known — just applied to full-screen screenshots instead of crops. Video compression settings (`libx265`, `crf 28`, `medium` preset, `hvc1`, `yuv420p`, `aac 128k`) are also unchanged; this ADR doesn't touch ADR-009's encode step.

**This does not mean the prior region-crop design was a mistake.** It was the correct call given the priorities at the time (live-player byte savings mattered, video export didn't exist yet). The priorities changed once ADR-009 landed; this ADR documents that change, not a correction of an error.

**Verification performed:**
- Regression: re-ran `node scripts/export-video.mjs replay/test-scenarios/scenario-1 --narration=short` (no asyncWait event, exercises the unrelated `move`/`circle`/`click` phases) — still produces a valid 1280×800 `hevc`/`hvc1`+`aac` mp4, 7.0s, ~172KB. Confirms the asyncWait changes didn't regress the rest of the pipeline.
- New: built a small synthetic scenario (`replay/test-scenarios/scenario-asyncwait` — a placeholder "export tool" page with a 6-frame progress-bar/spinner sequence, since the only existing fixture with a real asyncWait event, `replay-app/public/test-scenarios/demo-gallery`'s kitchen-sink-derived manifest, has an empty `screenshots/` folder — its `regionRect`-shaped asyncWait event was authored by hand for the prior session's manifest-type work and was never backed by a real capture, so there were no actual image bytes to render). Ran the full export pipeline against it: `frame-plan.json` → 108 frames @ 30fps, 3.6s total → Pillow rasterize → ffmpeg encode → `hevc`, 1280×800, 3.6s, **23,258 bytes**. Visually inspected the first and last asyncWait frames (extracted via `ffmpeg -vf select`) — progress bar and spinner advance coherently frame to frame, cursor stays parked at the triggering click's position, no layout-shift artifact.
- **No true region-crop-version size to diff against for an asyncWait scenario specifically** — ADR-009's verification pass only covered `scenario-1`, which has no asyncWait event, so this is the first asyncWait scenario ever actually rendered to video. The comparison the pivot is justified by (h265 handles full frames fine without manual cropping) is therefore argued analytically here, not measured against a prior export — flagged honestly rather than fabricating a before number.

**Consequences:**
- `docs/roadmap.md`'s `asyncWait` entry and `docs/open-questions.md`'s "Element-region screenshot compositing" entry both still describe the now-superseded region-crop design in detail (drift/resize risks included) — left as historical record per house practice (see ADR-008/ADR-009 precedent of amending rather than deleting), with a note added at each pointing to this ADR.
- **Newly discovered, separate, NOT fixed by this ADR:** `buildTimeline()`'s move-phase-after-asyncWait computes its duration from the raw gap between the asyncWait event's manifest `timestamp` and the next event's `timestamp` — both real wall-clock capture times. Since the asyncWait event's `timestamp` is recorded at the *start* of the real wait (consistent with every other event), and the next event's `timestamp` is recorded after the real wait already elapsed, that gap is the entire real wait duration, tens of seconds, not the compressed `frameDurationMs`. Nothing currently re-bases this — a manifest with a real event immediately following an asyncWait would (re)introduce a multi-second-to-tens-of-seconds "dead air" glide phase right after the compressed wait, undermining the very compression this feature exists to provide. This pre-dates this ADR's changes (not introduced by the region-crop removal) and was only noticed while building the verification scenario above; not fixed here, flagged for follow-up.
- `replay-app/public/test-scenarios/demo-gallery/manifest.json`'s kitchen-sink asyncWait event is now in the old, unsupported shape (`regionRect` present, no `screenshots/` files backing it at all) — needs either a real Playwright capture re-run against the kitchen-sink demo, or manual migration to the new shape, before that fixture is usable for anything. Not fixed here since no real screenshots exist to migrate to.
- Video export and both live players now agree on one `AsyncWaitAction` shape with no compositing step — removes the third copy of "how do we draw an asyncWait frame" that would otherwise have needed to track the same drift/resize-risk fixes the old design would eventually have needed.
